## Measured API performance

Node 24.21.0, Windows, SQLite, localhost. Results include downloading and parsing JSON, with no network delay imposed. Concurrent tests use overlapping requests with one authenticated administrator session; they do not represent 20 separately active browser users. All measured requests succeeded.

| --- | ---: | ---: | ---: | ---: | ---: |
| Full state, before seeding (20 documents) | 30 | 1 | 1.4 ms | 2.6 ms | 627 req/s |
| Full state, 1,000 documents | 60 | 1 | 28.9 ms | 33.6 ms | 33.9 req/s |
| Full state, 1,000 documents | 60 | 5 | 80.9 ms | 94.2 ms | 60.0 req/s |
| Full state, 1,000 documents | 60 | 20 | 353.5 ms | 384.0 ms | 54.5 req/s |

The full state response increased from about 48 KiB to 2,039 KiB. Importing the generated backup took approximately 569 ms. A server memory observation after the API workload showed about 71 MiB working set and 66 MiB private memory; these are observations, not peak measurements.

## Assessment and limits

The tested screens remained responsive with 1,000 documents. No performance fixes to application code were needed for this run. Reports navigation was the slowest measured secondary screen, but was sampled only once.

The main scaling cost is the full `/api/state` payload: document pagination happens in the browser, so a page of rows still requires the complete registry and all embedded histories. Version polling is small; a changed state requires the larger fetch. Server-side pagination and incremental state updates would be relevant areas to investigate if record/history volume or concurrent usage grows.

This was a short local load test, not a long-duration soak test or a measurement over the office network. It establishes behavior for this synthetic mix on this machine, not a maximum supported document count or production user capacity. The synthetic bulk import was generated offline through the engine; the benchmark separately exercised real API reads and comment writes. It did not benchmark the creation of all 1,000 records over HTTP or 20 independent browser sessions.

## Repeat or restart

Start the dedicated demo from the application directory:

```powershell
$env:HOST='127.0.0.1'
$env:PORT='3131'
$env:DATA_DIR='.test-runs/stress-1000-20261007'
$env:SEED_DEMO='1'
$env:TZ='Asia/Manila'
node server.js
```

`node test/stress-1000.js` regenerates the dedicated stress dataset and reruns the API measurements. It replaces documents on port 3131; it refuses a dataset containing unrelated records. The generator saves the previous dataset backup before importing. `node test/stress-browser.js` measures browser screens, with Playwright available in Node's package search path and Microsoft Edge installed.

Raw evidence is in `.test-runs/stress-1000-20261007/`: `api-performance.json`, `browser-performance.json`, `dashboard-1000.png`, `graphs-1000.png`, and `staff-actions-1000.png`. The generated backup is also retained there. Backup files contain demo credential hashes and should be treated as local test artifacts.
