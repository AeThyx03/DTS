## D07 — Metadata edits start the processing clock before assignment

**Location:** [engine.js:545](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/engine.js:545>), [engine.js:548](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/engine.js:548>).

Register a received document using a type with a three-working-day threshold, without forwarding or assigning it. Its `clockStart` and `dueAt` are initially null. Edit only its subject. The API returns 200 and stores a clock start and due date even though status remains `received` and assignee remains empty.

The reproduction used receipt on 13 October 2026. Editing produced a 16 October deadline. The edit path calls `computeDeadline` using receipt time whenever the processing clock is absent, then writes the returned start time. This conflicts with the configured deadline's “from assignment” basis and can make a document overdue before anyone is assigned to process it.

**Suggested correction:** Preserve an unstarted assignment-based clock during metadata edits. Validate and calculate a prospective edit before mutating the record; distinguish reporting-period clocks from assignment-based clocks.

## D08 — Editing bypasses registration validation

**Location:** [engine.js:531](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/engine.js:531>), [server.js:523](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/server.js:523>).

A permitted edit with a valid subject successfully stored `source: ""`, `division: "NO_SUCH_DIVISION"`, `commType: "NO_SUCH_COMMUNICATION"` and `priority: "banana"`. The API returned 200. Registration rejects corresponding invalid values, but the edit payload cleaner only trims strings and the engine copies most fields without validating them.

This allows records with no valid routing division or communication type. A user can also clear the source using the ordinary edit form. Restricting dropdown choices in the UI does not validate direct API requests.

**Suggested correction:** Validate the complete proposed document against shared registration/edit rules before applying it. Explicitly handle existing inactive reference values without accepting unknown references or blank required fields.

## D09 — Failed reporting-period validation is ignored during edits

**Location:** [engine.js:533](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/engine.js:533>), [engine.js:546](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/engine.js:546>).

Create an ordinary received document, then edit its type to `Consolidated CMR and PPR` with an empty reporting period. The API returns 200 and stores that type with an empty period, no due date and no assignee. The edit path mutates the document first, calls `computeDeadline`, and merely skips the calculated fields when `x.ok` is false; it still reports success.

The equivalent new registration requires a reporting period and configured regional responsibility. The edit can therefore produce a report that bypasses those requirements.

**Suggested correction:** Reject unsuccessful deadline validation before saving any proposed changes. Define and validate whether converting between region-routed and ordinary document types is allowed and how routing must change.

## D10 — Renaming a document type orphans its existing records

**Location:** [server.js:915](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/server.js:915>), [server.js:924](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/server.js:924>), [engine.js:283](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/engine.js:283>).

Renaming the configured `Consolidated CMR and PPR` type through the reference-list API succeeds. Eight probe records retained the original name, but `docTypeOf(originalName)` then returned null and `isRegularDoc(originalName)` returned false. The active reporting-period safeguard still passes because the renamed type remains active.

Records use the mutable type name as their reference. Unlike communication types, the server does not prohibit removal of a used document-type name or migrate document references on rename. Existing regular reports can disappear from regular-report calculations and lose their configured deadline/routing interpretation.

**Suggested correction:** Use stable reference IDs, or transactionally migrate all dependent references when renaming. Until then, block renaming/removing used types and offer deactivation. Include workflow definitions/modes and report-schedule type references in dependency handling.

## D11 — Forwarding can strand new work at an inactive focal

**Location:** [engine.js:211](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/engine.js:211>), [engine.js:427](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/engine.js:427>), [engine.js:456](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/engine.js:456>).

Deactivate CMED's configured focal, then register and forward a new CMED document. Creation succeeds and stores status `at_focal`, although the nominated focal is inactive. `divFocal` returns the user without checking `active`; forwarding only checks whether a focal object exists.

That account cannot sign in, and normal assignment is tied to that division's focal. An administrator must repair the configuration or override the route.

**Suggested correction:** Refuse forwarding to an inactive focal, surface a clear configuration error, and decide how deactivation should handle existing focal responsibilities.

## D04 — Operational reports omit generated Special Reports

**Location:** [client.js:1085](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/client.js:1085>), [client.js:408](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/client.js:408>).

The registry and Analytics/Graphs combine ordinary documents with `specialDocRows()`. `buildReport`, which produces the Reports page's tables, CSV and print data, starts with ordinary `visibleDocs(u)` only.

With one overdue generated Special Report and no overdue ordinary documents, the registry-derived set contained one overdue report while the operational Overdue report returned zero rows. Staff workload and other generic report datasets have the same omission.

**Suggested correction:** Establish a shared reporting dataset or explicitly label and separate ordinary-document reports. Preserve Special Report IDs, histories, permissions and applicable fields when combining them.

## D01 — Large working-day thresholds produce a weekend deadline

**Location:** [engine.js:122](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/engine.js:122>), [engine.js:309](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/engine.js:309>), [engine.js:696](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/engine.js:696>).

Set a reporting-period document type to 25 working days, reporting January 2026, with no additional holidays. The ordinary deadline function returns 28 February 2026, a Saturday. The Special Report function for the same count returns 6 March 2026, carrying the working-day count forward.

`nthWorkdayOfMonth` falls back to the final calendar day if its requested working day does not exist. Configuration permits thresholds well above a month's working-day count.

**Suggested correction:** Define one policy for overlong thresholds: reject them or carry the count forward consistently. A working-day deadline must not silently become a weekend date.

## D02 — Monthly release figures omit older backlog

**Location:** [client.js:676](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/client.js:676>), [client.js:713](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/client.js:713>), [client.js:774](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/client.js:774>).

Prepare two September releases: one received in August and one received in September. Select September only. Both the released chart and the “Released in the reporting period” KPI show one, although two documents were released that month.

The data is restricted to received-in-period records before release dates are counted. A received cohort can be useful, but that is narrower than the release-period labels imply.

**Suggested correction:** Calculate intake and release metrics from their own event dates over the relevant authorized population. Alternatively, explicitly label receipt-cohort results; do not present them as the complete release count.

## D03 — No selected month includes all-time records

**Location:** [client.js:680](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/client.js:680>).

In Several months mode, clear every selected month. `periodLabel()` says “no month selected”, but `periodDocs()` returns all records because its month filter only runs when the month array is nonempty. The controlled two-document example returned both documents.

**Suggested correction:** Return an empty dataset or an explicit missing-period state when no month is selected. An all-time option should be intentional and labelled.

## D05 — Desk-age drill-down does not select the clicked band

**Location:** [client.js:768](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/client.js:768>).

Invoke the current handler with “8 or more working days”. It applies only `{ tile: "ongoing" }`, discarding the selected value. The resulting list contains all ongoing records, rather than the records behind that chart bar.

**Suggested correction:** Add an age-band predicate shared with the chart, and preserve relevant reporting-period/division context when drilling down.

## D06 — Other configuration handlers still announce failed saves as successful

**Location:** [client.js:1117](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/client.js:1117>), [client.js:1149](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/client.js:1149>), [client.js:1162](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/public/client.js:1162>).

The newly fixed Settings handler waits for the server, but role/OIC and other older configuration handlers still mutate local state, call `cfg()` without awaiting it, and immediately show success.

Executing the actual permission-change handler with a rejected API response produced both “Permission updated.” and a server-rejection error. `cfg()` does not return an explicit save result to its callers. Offline refresh failures can also leave the optimistic local display uncorrected.

**Suggested correction:** Make shared configuration saves return success/failure, await them, and display success only after confirmation. Restore or refresh rejected local changes and protect against conflicting whole-section saves.
