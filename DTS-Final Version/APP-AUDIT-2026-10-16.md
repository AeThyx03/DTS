### A10 — Failed restore changes the database

**Locations:** [restore validation and transaction](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/server.js:997>), [post-commit load](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/server.js:1029>), [holiday rebuild](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/engine.js:99>).

Starting from a valid isolated backup, change only `holidays` to `[null]` and restore it. The endpoint returns HTTP 500 when `rebuildHS()` reads the null holiday's date. A separate read-only SQLite connection confirms `[null]` was already committed. Startup uses the same loader, so the persisted invalid configuration can also prevent a later restart from completing. That restart consequence follows from the loader code; a restart of the live app was not attempted.

**Correction:** Validate nested structures, enums and relationships and successfully construct the proposed replacement state before committing it. Reject invalid input without altering either the persisted or in-memory state. Preserve a recovery snapshot for a valid restore.

### A02 and A01 — Editing does not preserve registration and clock invariants

**Locations:** [document edit](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/engine.js:536>), [deadline recomputation](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/engine.js:552>), [API payload cleanup](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/server.js:523>).

A permitted edit returned 200 and stored `source: ""`, `division: "UNKNOWN"`, `commType: "UNKNOWN"` and `priority: "banana"`. A separate ordinary document was changed to `Consolidated CMR and PPR` without a reporting period or designated assignee; that also returned 200. The engine mutates the document before deadline validation and does not reject a failed calculation.

Separately, create an unassigned, received document with a three-working-day document type, then edit only its subject. Its clock changes from null to a receipt-based start and gains a due date, although its status remains `received` and its assignee remains empty. This conflicts with the configured deadline description, which says it starts from assignment.

**Correction:** Validate a complete proposed record using shared registration/edit rules before mutating it. Reject invalid conversions and deadline results atomically. Preserve an unstarted assignment clock during metadata-only edits; handle reporting-period clocks separately.

### A03 and A09 — Mutable reference names can orphan dependants

**Locations:** [division validation](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/server.js:925>), [document-type normalization](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/server.js:942>), [reference dependency checks](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/server.js:950>), [reporting ownership](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/server.js:534>).

Renaming the configured consolidated-report type succeeded while seven isolated documents retained the old type name. The old type no longer existed in reference configuration. Document-type lookups and regular-report classification depend on that mutable name.

With no ordinary documents, removing CMED also succeeded despite personnel and a generated Special Report depending on it. The personnel retained `division: "CMED"`; the report remained stored but no longer resolved into CMED reporting results. The removal check considers only ordinary documents' stored division. SQLite's foreign-key check does not detect these JSON relationships.

**Correction:** For this architecture, initially block removal/renaming of references with any dependants and offer deactivation. If renaming is supported, update every dependant transactionally, including users, reports, designations, schedules/configuration and workflow references where applicable. Stable IDs can be considered separately; this audit does not require a database migration.

### A06 — Regular-report registration creates inconsistent division attribution

**Locations:** [browser division fallback](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/client.js:1043>), [engine fallback](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/engine.js:419>), [Insights filter](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/client.js:692>), [server reporting ownership](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/server.js:534>).

In the actual browser form, an Admin user logged a consolidated report for a region whose designated person belongs to CMED. The division control is hidden for this report type. Before submitting, the client fills the hidden division from the logger, so the server receives the valid division `Admin` and retains it. Its assigned person belongs to CMED.

The CMED scoped endpoint includes the report using personnel ownership. The CMED Insights filter excludes the same report because `periodDocs()` uses its stored `division`. This reproduces the mismatch without modifying an existing record. Stored division also participates in division-manager selection, so it should not be casually rewritten on existing workflow records.

**Correction:** Derive new regular reports' division from the designated person on the server. Use one stable reporting-ownership definition across CMED/CMSD and Insights while preserving workflow-routing semantics. Define any treatment of existing mismatched records explicitly.

### A07 — Shared Special Reports are attributed differently by viewer

**Location:** [Special Report adapter](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/special.js:76>).

Use a processing Special Report with blank stored/workflow division and two active assignments, one CMED and one CMSD. The browser adapter chooses the current user as assignee when that user is assigned. It then derives division from that selected person. Calling the current adapter for the two users returns CMED and CMSD respectively. Insights consumes those adapted rows. The secure scoped endpoints correctly exclude the mixed-ownership report from both division reports.

**Correction:** Separate viewer-specific action responsibility from reporting ownership. Keep assignment actions intact, but use a consistent shared/unresolved ownership rule for reporting, independent of who is viewing it.

### A11 — Released Special Reports are absent from release totals

**Locations:** [browser adapter](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/special.js:78>), [server saves workflow release date](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/server.js:444>), [chart volume](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/client.js:729>), [Analytics released total](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/client.js:790>).

The server stores Special Report release time in `item.workflow.outAt`. The browser adapter carries several workflow fields into its document-shaped row, but omits `outAt`. A synthetic released report with a valid February workflow release date produced no adapted release date, an Analytics released total of zero and a Charts released total of zero for February.

**Correction:** Carry the canonical release timestamp through the shared reporting adapter and verify Analytics, Charts, print and exports using a released Special Report, including one received in an earlier month.

### A04 — Forwarding to an inactive focal succeeds

**Locations:** [focal lookup](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/engine.js:216>), [forward guard](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/engine.js:427>), [forward action](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/engine.js:460>).

Deactivate CMED's configured focal, then log and forward an ordinary CMED document. Registration succeeds and the document reaches `at_focal`. The lookup returns an existing user without requiring an active account, even though inactive accounts cannot sign in. Administrative intervention is then needed.

**Correction:** Require an active, eligible focal before forwarding and handle focal responsibilities when deactivating users.

### A05 — Concurrent account creation permits duplicate usernames

**Location:** [uniqueness check and asynchronous password hashing](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/server.js:869>).

Two simultaneous creation requests using the same username both returned 200 and created two users. Each passes the uniqueness check before awaiting password hashing. Login uses the first username match.

**Correction:** Recheck uniqueness after hashing in the current single-process implementation and ensure create/update operations preserve case-insensitive uniqueness. A database-level invariant is a possible later strengthening, subject to the existing no-migration constraint.

### A08 — CSV text is escaped for CSV syntax but not spreadsheet formulas

**Location:** [CSV helper](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/client.js:89>).

The current helper exports `=1+1`, `+1+1` and `@SUM(A1:A2)` unchanged. User-entered source, subject and reference fields use this export path. This confirms the exported bytes; opening the file in Excel or another spreadsheet application was outside this audit.

**Correction:** Apply an explicit spreadsheet-safe text policy to user-controlled fields while preserving intentional numeric values.

### A13 — A working-day threshold can produce a weekend deadline

**Locations:** [month-bounded helper](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/engine.js:122>), [ordinary reporting deadline](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/engine.js:315>), [Special Report overflow handling](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/engine.js:701>).

With no holidays and a 25-working-day reporting-period threshold for January 2026, the ordinary calculation returns **28 February 2026**, a Saturday. The equivalent Special Report calculation returns **6 March 2026**. Configuration accepts the larger threshold, but the ordinary helper returns the month's final calendar day once the requested working day does not fit.

**Correction:** Specify a consistent overflow rule or reject thresholds that cannot fit the relevant month. A working-day deadline should not silently fall on a non-working day.

## Access-policy boundary, not an assumed defect

**P01:** [unscoped state response](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/server.js:593>) and [global document visibility](<D:/test server/staging-dts/New folder/dts-final version-workflow/DTS-Final Version/.deployment-backups/audit-corrections-20261016-084600/public/engine.js:271>).

The CMED/CMSD tabs and scoped endpoints enforce division access. A CMED-only fixture user received 403 for the CMSD scoped endpoint. That user could still read CMSD records through the unscoped state response used by the department overview; the probe found ten such demo records. This matches the preserved global department-view policy and is not counted among the 12 defects.

Before building features that assume division confidentiality, decide whether the restriction concerns only division destinations or all document access. Sidebar visibility alone does not establish global data isolation. No access-policy changes were made during this review.
