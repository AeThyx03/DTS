# Project analysis — 15 October 2026

## Scope and result

Reviewed application source, deployment files, documentation, and test infrastructure. Ran the nine default API regression suites using fresh demo databases, plus focused probes for restore validation and concurrent user creation. No application source or existing `data` records were changed. Browser suites were not rerun. This is a focused code and behavior review, not a comprehensive security or production capacity assessment.

All nine regression suites passed. Eight suites reported **477 checks passed, zero failed**; the workflow suite also passed its assertions without a numerical summary. Application JavaScript syntax checks passed.

## Findings, in priority order

### 1. High — malformed restore data can be committed before validation fails

**Location:** `server.js:971–1008`, particularly the initial checks at line 975 and `loadAll()` at line 1004; `public/engine.js:99`.

Restore checks a few top-level fields, replaces persisted records inside a transaction, commits, and then loads the replacement state. It does not fully validate the nested configuration before committing.

**Confirmed reproduction:** Exported an isolated demo backup, changed only `holidays` to `[null]`, and restored it. The endpoint returned HTTP 500 when `rebuildHS()` read `h.date`, but a separate read-only SQLite connection confirmed that `[null]` was already persisted. Startup calls the same loader, so the invalid data can also prevent a later restart from completing until the database is repaired or replaced.

**Recommended change:** Validate all backup structures and references, and construct a valid replacement state before replacing persisted records. Invalid input must leave the previous database and in-memory state intact. Preserve a recovery backup before applying a restore.

### 2. Medium — concurrent requests can create duplicate usernames

**Location:** `server.js:845–848`; users table definition at line 32.

The uniqueness check runs before awaiting password hashing. Two requests can both pass the check before either adds the new user. The database only constrains the user ID, not the username stored inside the JSON.

**Confirmed reproduction:** Submitted two simultaneous user creation requests with the same username. Both returned HTTP 200, and the state contained two users with that username. Login selects the first matching account, making access ambiguous.

**Recommended change:** Enforce case-insensitive username uniqueness in SQLite, with an appropriate migration for existing duplicates, and map constraint conflicts to a clear client error. Rechecking after hashing can close the immediate race in the current single-process design, but a database constraint is the stronger invariant.

### 3. Medium — CSV exports preserve formula prefixes

**Location:** `public/client.js:89–94`, with user-entered document fields exported at line 572.

The CSV helper escapes separators, quotes and newlines, but leaves values beginning with `=`, `+`, `-` or `@` unchanged. User-entered subjects, sources and reference numbers can therefore reach spreadsheet software as formula-like cells.

This finding is based on source inspection; opening exports in spreadsheet applications was outside this review.

**Recommended change:** Apply a spreadsheet-safe text policy to exported user-controlled cells, including formula-prefix handling. Preserve legitimate numeric fields deliberately.

## Product and maintenance observations

- **Workflow execution remains incomplete by design.** Workflow definitions can be edited, published, forked and simulated, but `server.js:615` rejects `ENGINE` activation. Live documents still follow the legacy engine. Published diagrams do not execute assignments, approvals, notifications or status transitions. `WORKFLOW_ENGINE.md` accurately documents this boundary.
- **All authenticated users can read all ordinary documents.** `public/engine.js:266` returns true for any signed-in user, and `/api/state` uses that function. Action permissions remain separate. This is an observable access policy, not an assumed defect; any need for division-level confidentiality would require server-side changes.
- **Full-state synchronization is the principal scaling cost.** `/api/state` sends all visible documents and their histories; registry pagination is performed in the browser. Prior stress reports describe this limitation, but their October 7 performance measurements were not rerun here.
- **Large modules increase change risk.** The main browser module is about 162 KB and the server about 93 KB. Extracting authentication, persistence and API domains into modules would make future runtime workflow integration easier to review.
- **Default test coverage is easy to miss.** `npm test` runs only `api.test.js` against a separately started server. The isolated runner is the more complete entry point: `node test/run-regression.js`.
- **This directory is not a Git checkout.** Git status could not establish a baseline or identify earlier local modifications.
